# AXNODE — 독자 섹터형 초경량 프로그램 파일/런타임 최종설계도 v1.0 (설계 기준)

**기준일:** 2026-11-13 KST · **제품 ID:** AXNODE · **브랜치:** `product/axnode-sector-runtime` · **단계:** 독자 파일 규격 A안 승인, 전체 수용조건/가중치 세부 승인 대기 · **공식 최종완성률:** UNASSESSED · **출시/판매:** RELEASE HOLD / 크몽 미등록.

> 사용자가 확정한 **핵심 구상과 A안**을 기준으로 한 전체 목표 설계. 아래 상세 R01~R29는 구현/검증 기준 제안이며 사용자의 개별 가중치 확정 전 공식 퍼센트 산정 금지. POC의 19 PASS를 상품의 95% 등으로 환산하지 않는다.

## 1. 왜 존재하는가 — 제품 정의와 반드시 지킬 원형

하나의 프로그램을 통째로 실행기/클라우드/저장소에 복제하지 않고, **한 개의 독자 바이너리 확장자 파일** 안에 초경량 중앙 제어 섹터·기능 섹터/섹터 인덱스·자원 참조 섹터·실행 순서·상태/복구 계약을 기록한다. 각 섹터는 실제 코드/데이터를 파일 내부에 넣거나 로컬, NAS, 사용자 허가를 받은 원격 저장소/실행 환경을 가리킨다. 요청/예약/안전한 외부 트리거가 발생하면 적합한 실행기가 파일을 읽고 필요한 부분을 **지연 해석/호출**, 앞선 단계 결과에 따라 뒤 단계를 진행하며 최종 결과/영수증을 반환한다. 사용자는 하나의 프로그램처럼 취급한다.

예시: 3GB 소프트웨어의 *제어/자원 참조 파일*은 수백 바이트~수 KB일 수 있다. **3GB가 사라지거나 압축되는 것은 아니며**, 실제 실행 위치에는 필요한 코드·모델·데이터와 CPU/RAM이 있어야 한다. 무료 서비스에는 한도, 네트워크·전송 비용, 약관이 있다. '무제한 무료 분산 클라우드'는 고객 약속/출시 기준에 포함하지 않는다.

### 사용자 목적
1. 원래 프로그램/데이터와 독립된 하나의 이동 가능한 `.axnode` 파일로 실행 방식을 선언.
2. 파일의 고유 섹터들이 반도체의 연결망을 연상시키듯 **이름·ID·주소·입출력·조건**으로 관계를 형성.
3. 연결/권한/자원 위치가 달라도 안전하게 필요한 섹터만 불러오고, 느리더라도 최종 결과를 생성.
4. GitHub 등 이벤트 실행기는 **선택적 어댑터**. 로컬·완전 오프라인 실행도 지원.
5. 장기적으로 HAE/Lightning Azent가 생성한 *승인된* 실행 계획을 AXNODE로 패키징하여 고객 업무 AX 배포에 활용.

## 2. 설계 대안 비교 및 채택

| 항목 | A 독자 바이트 포맷/섹터 런타임 (채택) | B ZIP/기성 컨테이너 안에 메타데이터 |
|---|---|---|
| 제어/섹터 인덱스 | 고유 헤더·주소·해시·버전 직접 정의 | 컨테이너 파일 색인 재활용 |
| 성능 | 섹터별 임의 접근/스트리밍 최적화 여지; 초기 버전 우위 미증명 | 성숙한 압축/도구 재사용 |
| 개발비/유지 | 규격·검사기·호환성 자체 책임, 초기 비용 큼 | 낮음, 기존 생태계 활용 |
| 보안 | 고유 파서 취약점·호환성 위험, 엄격한 fuzz/서명 검증 필수 | 기존 라이브러리 검증 활용 가능 |
| 네트워크·무료 실행 | 둘 다 외부 실행기·할당량·자원 권한 필요 | 동일 |
| 결정 | **사용자 선택 A안.** 비용 증가를 감수하고 독립 규격을 개발 | 백업 설계, 무단 전환 금지 |

`.axnode`는 포맷 식별자이며 그 자체가 OS 실행 파일은 아니다. 호환 런타임/런처가 반드시 필요하다. 기존 HAE/LA/PREP/SMAX 등 원본 저장소와 기술 책임은 유지.

## 3. 바이너리 파일 규격 — Draft v0.1 실증과 장기 v1 목표 분리

### POC v0.1 확인된 부분
- 64바이트 헤더 `<8sHHIQQ32s`(little-endian): magic `AXNODE1\0`, major/minor, sector_count, index_offset, index_size, index SHA-256.
- `HEADER | sector payloads | INDEX` 순서. 자체 인덱스 엔트리 `<16sBBHQQ32sH>` + UTF-8 섹터명: ID, kind, flags, offset, size, payload SHA-256, name.
- 섹터 유형: `CONTROL`(1), `INSTRUCTION`(2), `RESOURCE`(3). 중앙 제어 섹터는 정확히 하나. 고유 이름, 인덱스·페이로드 해시 및 오프셋 검사.
- POC `INSTRUCTION`은 `AXOP` + opcode + JSON 인자, 명령 3종만 허용: `LOAD_CSV`, `SUMMARIZE`, `WRITE_REPORT`; 3단계 선형 실행/5섹터 CSV 예제.
- POC 제한: 파일 64MiB, 자원 10MiB, CSV 100,000행, 섹터 64개. 이는 **초기 안전 가드**이지 상용 3GB 지원 근거가 아님.
- SHA-256은 변조/손상 *탐지*이며 게시자 인증·서명·안전한 원격 코드 실행을 뜻하지 않는다.

### 목표 v1 파일 구획
1. **Header:** 고정 magic, 버전/feature bits, 인덱스 위치/크기, 바이트 순서, 암호화/압축/서명 정보 식별.
2. **Sector directory:** 영구 섹터 ID, 타입, 논리 이름, 오프셋/크기, 압축·참조 모드, 타입 계약, 콘텐츠 다이제스트 및 의존성.
3. **Control graph:** entrypoint, typed ports, 조건·분기·합류·반복 상한, timeout, 의존 DAG 및 순서 보장.
4. **Inline sectors:** 작은 선언형 명령, 공개 메타데이터, 선택적 고객 허가 데이터; 무단 비밀 키/개인정보 포함 금지.
5. **External resource descriptors:** `local-asset`, `approved HTTPS object`, `NAS share`, `version-pinned repository artifact` 등 모드·주소·다이제스트·최대 크기·허용 능력. GitHub repo 자체가 임의 원격 실행기인 것처럼 표시 금지.
6. **Execution policy:** 허가된 기능/입출력/네트워크/CPU·RAM·시간 예산/호출 횟수/재시도 규칙; 소유자/고객 승인 범위.
7. **Signature/provenance:** 포맷 파서 내 검증 가능한 서명/신뢰 루트·서명키 회전/철회·재현 가능한 빌드/아티팩트 목록. 콘텐츠 해시만으로 공급망 신뢰 확보 불가.
8. **Receipt/checkpoint references:** 실행 상태는 원본 파일의 불변 버전과 분리해 안전 저장; 단계별 입력·출력 해시·완료 여부·오류·승인 증거 연결.
9. **Forward compatibility:** 알 수 없는 필수 기능은 fail closed, 선택 확장만 건너뛰기, 명시적 포맷 변환·이전.

**섹터**는 논리 실행 단위이지 CPU 캐시/하드디스크 물리 섹터가 아니다. 동시 실행과 원격 호출은 계획된 후속 기능으로만 표시한다.

## 4. 런타임 실행 경로

`Request/Trigger → Resolve immutable .axnode → parse/validate → approve policy/preflight → resolve sector dependencies → fetch/cache verified content → safe typed interpreter or isolated permitted worker → checkpoint and receipt → result and report`

- **트리거:** 로컬 CLI/GUI, 일정, 승인된 GitHub Actions `workflow_dispatch`/예약/저장소 이벤트, 허가된 고객 내부 실행기. 외부 이벤트 수신 인증·중복 방지 필수.
- **해석/계획:** 그래프 타입·입출력·사이클·도달성·타임아웃·자원 크기·권한을 실제 데이터 접근 전 검증.
- **획득:** 섹터별 선택 로딩, immutable digest, ETag/버전 고정, 로컬 캐시, 연결 끊김 시 정해진 폴백. 오염 캐시·TOCTOU·네트워크 재시도 한도 시험.
- **실행:** 첫 단계는 명령 allowlist 기반 안전 VM; 장기적으로는 서명된 WebAssembly/제한된 워커 등 *별도 격리* 어댑터 검토. 임의 내려받은 Python `exec`/쉘 자동 실행 금지.
- **복구:** 실행 `run_id`, step state, idempotency key, transaction/compensation(가능 범위), 재개 시 입력 해시 검증. 결제/삭제/외부 전송은 재실행 전 고객 재승인 또는 멱등성 영수증 필수.
- **결과:** 사람이 읽을 수 있는 성공/실패/부분성공, 정량 로그/시간/네트워크 사용량, 상세 감사 영수증. 원본 파일 기본 불변.
- **대용량:** 3GB 시나리오는 데이터를 통째로 메모리에 올리는 것이 아니라 분할/스트리밍 처리·로컬 임시 스토리지/디스크 사용량 한도 검증으로 접근.

## 5. 안전·권한·실제 무료 운영 경계

- 파일을 하나 받는 것만으로 호스트 명령/외부 네트워크를 실행시키지 않는다. 먼저 정적 검사→사용자 권한 승인→서명/해시/allowlist 확인→샌드박스.
- 경로 탐색·symlink 탈출, archive/decompression bomb, oversized length/offset integer overflow, 모듈 탈취, 서버 SSRF, 리다이렉트, 공급망 변조, TOCTOU, fork-bomb, 비밀 유출, 로그 PII, 실행 비용 폭주에 대한 위협 모델/적대적 테스트.
- 비밀정보는 `.axnode`/GitHub에 저장 금지. 로컬 OS 자격 증명 보관소/권한 제한 secret broker, 범위·만료·회전·폐기 지원.
- 네트워크는 기본 거부 및 등록 도메인/주소·자료 항목에 따른 별도 동의. GitHub Actions 권한 `contents:read` 기본, 원본 고객 자료 업로드·공개 아티팩트 공유 금지.
- 무료 실행은 **고정된 무료 보장이 아니라 제공자 정책·계정/요금/할당량에 종속**. GitHub Actions는 영구 상주 서비스, 무제한 DB, 대용량 객체 스토어가 아니다. 예상 분/GB/API 호출, 캐시 및 비용 상한/비용 중지 게이트.
- 외부 코드/데이터 전송·서비스 계정 권한 변경·유료 CI·고객 데이터 활용·공개 배포는 사용자 사전 승인.

## 12. 2026-11-14 사용자 실기기 사례 — WORKNOVA Desk 분산 자원 실행 실증 시나리오 (설계 보강, 구현 아님)

**사례 근거/범위:** 사용자 Windows PC의 WORKNOVA Desk GUI 화면에서 한글 메인 창, 업무 탭 및 버튼이 표시된 사실은 관찰됨. WORKNOVA Desk는 PyInstaller `onedir` 방식 EXE 후보로 빌드되었고, 동일 배포 폴더의 `_internal/` 등 런타임 의존 파일을 필요로 한다. 이는 **WORKNOVA GUI 단독 구동 증거**이지 `.axnode`로 모듈을 분산 실행한 증거가 아니다. 현재 AXNODE 제품 브랜치에는 검증된 원격 로더·3GB 지원·Windows 통합 테스트가 없다.

### 12.1 제품 문제와 설계상 해결 경계

- **문제:** 사용자가 EXE만 떼어 다른 경로에 둘 경우 해당 빌드가 요구하는 Python 런타임/DLL/기타 라이브러리를 찾지 못할 수 있다. `onedir` 배포는 필요한 배포 디렉터리 전체의 일관성을 지켜야 한다. `onefile`로 한 파일 배포해도 실행 시 자원을 로컬 임시 위치에 추출하므로 원격 실행 문제의 자동 해법은 아니다.
- **AXNODE 적용 가설:** `.axnode`에 실행 계획, 로컬·USB·다른 드라이브·NAS·승인된 HTTPS 자원의 **위치/버전/다이제스트/의존 순서**를 선언하고, 전용 런처가 각 작업 전에 필요한 자원만 안전하게 조회·검증·캐시/스테이징하여 *지원하는* 작업을 수행한다. 자원 위치가 바뀌면 명시적 재지정·동일 해시 검증을 요구한다.
- **핵심 제약:** Windows 네이티브 DLL·확장 모듈은 OS 로더와 종속 파일 배치 규칙을 따른다. 임의의 원격 URL 또는 USB의 DLL을 검증 없이 동적으로 실행하지 않는다. 필요 시 버전 고정·서명 확인 후 로컬 격리 스테이징하며, 정식 서명·샌드박스 전에는 **데이터/안전 선언형 작업만 시연**한다. 프로그램의 필수 코드, RAM, 디스크, CPU 및 네트워크 전송량이 줄어든다고 보장하지 않는다.
- **장부 데이터 분리:** WORKNOVA SQLite 영업 장부와 백업은 EXE/AXNODE 실행 패키지 외부의 사용자 소유 경로에 유지하고, 기존 고객 DB를 자동 업로드·이동·변경하지 않는다. SQLite WAL 데이터베이스를 NAS 파일 공유로 여러 PC가 직접 동시에 열도록 설계하지 않으며 필요 시 별도 서비스/API 동기화 방식을 설계·승인받는다.
- **속도보다 완주 가능성:** 사용자 의도는 *지연되더라도* 안전하게 작업이 완료되는 것. 이는 무제한 대기/재시도가 아니다. 명시된 최대 대기·재시도 횟수, 가용성 판단, 오프라인 부분 실행, 캐시 만료, 수동 복구/재승인·정확한 오류 안내를 갖추어야 한다. 필수 자원을 확보하지 못하면 완료를 허위 보고하지 않는다.
