# AX ZERO — 아키텍처 대안·ADR

## ADR-001: 제품을 어디에 둘 것인가 (확정 2026-11-17)
- A 새 저장소 `hibi89/ax-zero`: 제품/릴리스 독립성 높으나 초기 repo/권한/연동 유지보수 증가.
- B `hibi89/Freelancer@product/ax-zero-local` 독립 제품 브랜치: 기존 product 브랜치 운영을 재사용, AXNODE 원본 보호, 초기 비용·작업 부담 최소.
- C `product/axnode-sector-runtime` 안에 합침: AXNODE 29요구/바이트 규격 변경 위험, 구현/검증 분모 혼동, 완료 시점 결합.
**선택 B**, 사용자 명시 지시. 성능차는 저장소 분할 때문이 아니라 런타임 구조·호출 비용에서 생긴다. 추후 공통 SDK 배포가 커지면 독립 저장소로 분리 가능하되 자동 이전/리포 변경 승인 아님.

## ADR-002: 실행 방식
- A 로컬 제한 IR+템플릿 기반 생성+독립 검증+정책 허용 목록 (**선택**): 시간/메모리 예측, 오프라인, 공급망 통제 유리. 모든 임의 자연어 작업 자동 프로그래밍은 불가능하므로 미지원 HOLD.
- B LLM이 무제한 Python/쉘을 매번 작성·직접 실행: 초기 개발 간단하지만 보안·재현성·정확도 위험과 GPU 시간 증가.
- C AXNODE 완성 후 바이너리 런타임에 먼저 얹기: 향후 배포 장점이나 AXNODE 미완성에 종속. **미선택**.
따라서 Python/SQLite first, 생성 언어 확대는 플러그인 방식. AXNODE는 **후단 export adapter**로만 사용.

## ADR-003: 판단/분류
- 1차 구조 지문/스키마/규칙 기반, 2차 선택적 소형 임베딩/모델 추천, **3차 정책+독립 검사**. 유사도 수치만으로 승격하지 않는다.
- 신규 입력이 기존 검증 분포를 벗어나면 HOLD/AI fallback. 모델이 자신이 만든 검증기를 PASS로 판정하지 못하도록 trusted verifier 별도.
- 자동화 시작은 일상 로컬 읽기전용 작업, 외부 전송·삭제·권한은 별도 승인. 비검증 자동 self-healing 금지.

## ADR-004: 로컬 성능·유지보수
- 1050Ti/16GB RAM/Win11: GPU/모델 없이 반복 hot path, 구조화 IR+모듈 digest+SQLite 인덱스/캐시, process spawn 횟수 최소화, cold start vs warm start 각각 기록.
- UI는 동일 SQLite 읽기 API 사용; 웹 서버 상시 기동 필수로 만들지 않는다. 원칙적으로 CLI·데스크톱 로컬 우선, 필요 시 loopback-only local UI. EXE는 P2 실기기 검증 후.
- 자원 소비와 정확도는 독립 측정. 캐시 사용 이득만 '새 프로그램 생성 성공'으로 과대계상하지 않는다.

## ADR-005: 출시·소유권
- AX ZERO 독립 제품 ID, 최초 내부 사용; 크몽 19 SKU와 중복 신규 등록하지 않으며 상용 GO 전 출시 보류.
- 36 REQ 전체 유지. 실제 P1 코드 완료/공식 P2 검증/상용 출시/상품 등록은 별도 상태.
